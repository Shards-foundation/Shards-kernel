# Code of Conduct

## Our commitment

Shards-Kernel is an open-source project maintained for developers, researchers, and contributors working on governed AI systems. We want participation in this project to be professional, respectful, safe, and constructive.

We are committed to fostering a community where people can collaborate without harassment, hostility, intimidation, or discrimination.

This Code of Conduct applies to all project spaces, including:

- GitHub issues
- pull requests
- discussions
- code review comments
- project documentation
- linked community spaces used for project collaboration

It also applies when an individual is officially representing the project in public.

---

## Expected behaviour

We expect contributors and participants to:

- act professionally and respectfully
- assume good faith, while remaining honest and technically rigorous
- give constructive, evidence-based feedback
- focus on the work, not personal attacks
- be open to correction and discussion
- respect differences in background, experience, identity, and viewpoint
- avoid performative conflict, harassment, and disruption
- help maintain a project environment suitable for serious technical collaboration

---

## Unacceptable behaviour

Unacceptable behaviour includes, but is not limited to:

- harassment, threats, intimidation, or stalking
- hateful, discriminatory, or demeaning language
- personal attacks, insults, or inflammatory trolling
- sexual language or imagery in project spaces
- doxxing or publishing private information without explicit permission
- sustained disruption of discussions, reviews, or project workflows
- knowingly making false or misleading claims about contributors or the project
- deliberately wasting maintainer or reviewer time through spam, bad-faith reports, or abusive interactions
- encouraging or coordinating any of the above

Technical disagreement is not misconduct by itself. Strong critique is acceptable; abuse is not.

---

## Project standards

Because this repository concerns security- and governance-related infrastructure, we expect a higher-than-average standard of communication:

- claims should be evidence-based
- security concerns should be reported responsibly
- limitations, uncertainty, and blockers should be stated clearly
- “production-ready” claims should not be made casually
- contributors should not misrepresent tests, reviews, approvals, or deployment status

---

## Scope

This Code of Conduct applies within project spaces and in public interactions reasonably connected to the project.

Maintainers may consider behaviour outside official spaces when that behaviour has a direct impact on the safety, participation, or functioning of the project community.

---

## Reporting

If you experience or witness unacceptable behaviour, please report it privately:

**Email:** `shards-inc@engineer.com`

Please include, where possible:

- your contact details
- a description of what happened
- links, screenshots, or other relevant evidence
- any immediate safety or access concerns

Do **not** use public GitHub issues to report personal safety concerns or sensitive misconduct reports.

---

## Maintainer responsibilities

Project maintainers are responsible for clarifying and enforcing this Code of Conduct fairly and in good faith.

Maintainers may take any action they consider appropriate in response to unacceptable behaviour, including:

- private warning
- request to stop specific behaviour
- content removal
- temporary interaction restrictions
- rejection of contributions
- temporary or permanent ban from project spaces

Maintainers will aim to:

- review reports promptly
- protect reporter privacy where reasonably possible
- act proportionately
- document enforcement decisions internally where appropriate

Not every disagreement or unpleasant interaction will result in formal action, but clear misconduct may.

---

## Enforcement

Possible enforcement actions include:

| Level | Typical response |
|---|---|
| 1. Correction | Clarification, guidance, or request to stop |
| 2. Warning | Formal warning for inappropriate behaviour |
| 3. Restriction | Temporary lock, moderation, or limited participation |
| 4. Removal | Ban from discussion or contribution spaces |

The appropriate response depends on severity, pattern, and impact.

---

## Good-faith participation

We welcome:

- bug reports
- security-minded scrutiny
- disagreement over design choices
- evidence-backed criticism
- suggested improvements
- well-scoped pull requests

We do **not** welcome abuse disguised as “honesty” or “directness”.
